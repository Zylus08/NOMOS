### 1. Threat Model & Audit Scope

In autonomous scientific discovery, data leakage occurs when an agent inadvertently accesses ground truth simulator states, true parameters, or analytical derivatives rather than learning purely from noisy observations.

We audited five potential leakage channels:
1. **Attribute Leakage:** Do objects returned by `SimulationOracle` contain references to ground-truth physical parameters?
2. **Derivative Leakage:** Are analytical continuous derivatives ($u_t, u_x, \nabla^2 u$) secretly passed to the learner?
3. **Acquisition / Experiment Label Encoding:** Do candidate pool labels (e.g., `"wave_packet"`) encode semantic hints or target equations?
4. **Stopping Rule Introspection:** Does `IdentifiabilityAuditor` evaluate residuals against the hidden simulator?
5. **Architectural vs Process Boundary:** Does in-memory isolation in Python constitute an unbreachable security sandbox?

### 2. Empirical Red-Team Findings

#### Channel 1: Field Sanitization Audit
- **Inspection:** We queried `SimulationOracle.execute_experiment()` and probed all attributes of `resp.field`:
  ```python
  assert resp.field.true_parameters is None
  assert resp.field.u_clean is None
  assert resp.field.u_t_true is None
  assert not hasattr(resp.field, "_simulator")
  ```
- **Finding:** **PASSED.** `create_learner_field_observation` in `nomos/pde/isolation.py` creates a sanitized clone of the spatiotemporal array, setting all ground-truth fields to `None` and tagging provenance with `'isolated': True, 'leakage_protected': True`.

#### Channel 2: Derivative Calculation Audit
- **Inspection:** In `nomos/closed_loop/controller.py`, does the controller inspect `u_t_true`?
- **Finding:** **PASSED.** The controller builds its weak-form system entirely by numerical space-time integration against compact test functions ($\int u \phi_t dV$ and $\int u \phi_{xx} dV$), requiring zero external time-derivative inputs.

#### Channel 3: Semantic Label Encoding
- **Inspection:** Do candidate pool labels dictate the acquisition score?
- **Finding:** **PASSED.** `ExperimentAcquisitionEngine` iterates over tuples `(label, u0, cost)`. The acquisition score is computed strictly by evaluating vector fields $f_{h_1}(u_0)$ and $f_{h_2}(u_0)$ over the spatial array $u_0 \in \mathbb{R}^N$. The label string is used solely as an immutable key for audit logging.

#### Channel 4: Stopping Rule Independence
- **Inspection:** Does `IdentifiabilityAuditor` inspect the simulator?
- **Finding:** **PASSED.** The auditor inspects only `HypothesisPortfolio`, which contains hypotheses generated by WSINDy/Beam Search and evaluated on observed data. The true model is completely unknown to the auditor.

### 3. Critical Architectural Distinction: Data Sanitization vs Security Isolation

**Auditor Red Flag & Warning for Publications:**
It is critical to distinguish **data-schema sanitization** from **unbreachable process isolation**:
- In the current implementation, `SimulationOracle` and `ClosedLoopController` run inside the **same Python process memory space**.
- While software boundaries (private `_simulator` attributes, sanitized dataclasses, and strict functional passing) completely prevent standard algorithmic leakage, they do **not** form an OS-level sandbox. A malicious script with reflection (`gc.get_objects()`) could technically traverse heap memory to find the simulator instance.
- **Publication Requirement:** The research paper must explicitly state that `SimulationOracle` provides **data-flow sanitization and structural quarantine**, not OS-level hardware-isolated sandboxing. For hostile multi-tenant deployment, IPC socket serialization (e.g., JSON/gRPC over localhost subprocesses) should be utilized.
